# Decide what to build, buy or depend on

Compare making a component, adopting an existing one, buying a service and changing the requirement where those are credible options. Define the capability and acceptance scenarios first so each supplier or internal proposal is evaluated at the same system boundary.

## Evaluate a candidate

| Decision dimension | Evidence to request or produce |
| --- | --- |
| Fitness | Representative inputs, edge cases, measured limits, interfaces and operating assumptions |
| Assurance | Provenance, revision identity, known limitations and evidence applicable to the actual configuration |
| Operability | Diagnostic access, recovery path, update authority and responsibility during an incident |
| Economics | Integration and support labor, consumption model, lead times, minimum orders, replacement and exit |
| Control | Data portability, key custody, ability to run a previous version and notice of breaking changes |

A vendor service offering durable storage may acknowledge at a different boundary from the one your users rely on. Test the promised outcome using the consumer's interpretation. If the provider will not expose internal details, identify observable commitments and residual uncertainty. A second supplier using the same upstream fabrication source or identity service may share the first supplier's failure.

## Rehearse exit while the relationship is healthy

Select a representative asset with history, corrections, linked attachments and access information. Export it, verify completeness and import it into an independent reader. Estimate the time to migrate all assets at the measured transferable rate with new writes continuing. For physical systems, check interchangeability, tooling, certification assumptions, spare stock and requalification lead time.

Distinguish an easily replaced implementation from a deeply embedded data format, training requirement or licensing dependency. A thin adapter only reduces lock-in to the extent that semantics and operational behavior remain replaceable. Record the trigger for the next market or obsolescence review, the supplier relationship owner and the last practical exit date. Carry accepted dependency costs into [whole-life economics](../economics/lifecycle-and-resource-cost.md) and [interface evolution](../../../dependency-boundaries/contracts/evolution/compatibility-and-exit.md).
