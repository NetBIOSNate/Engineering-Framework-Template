# Industry frameworks and the evidence to produce

Use the source that answers the design question in front of the team. The mappings below are engineering interpretations for this template. Formal compliance, contract interpretations and sector-specific acceptance belong to the project's designated authorities.

| Reference | Design question | Apply it here |
| --- | --- | --- |
| NIST CSF 2.0 | Which security outcomes have owners and evidence? | Describe current and target outcomes. Link Govern to decision authority, Identify to asset and dependency scope, Protect to access and keys, Detect to independent signals, Respond to containment, and Recover to validated service. [NIST CSF 2.0](https://www.nist.gov/cyberframework/faqs) |
| NIST systems security engineering | Which trust assumptions and requirements survive design, integration, operation and retirement? | Trace one important property from the project brief to the implemented boundary and its negative test. Preserve the assumptions when a supplier or site changes. [SP 800-160 Vol. 1 Rev. 1](https://csrc.nist.gov/pubs/sp/800/160/v1/r1/final) |
| Well-Architected review | What does this architecture cost to secure, operate, recover, scale and sustain? | Apply the operational excellence, security, reliability, performance, cost and sustainability questions to two candidates. Use provider-specific material when evaluating a provider's actual service. [Google Cloud Well-Architected Framework](https://docs.cloud.google.com/architecture/framework) |
| Site reliability engineering | What user outcome is measured and which intervention is justified? | Define a denominator, objective and budget. Exercise a short spike, sustained failure and loss of the monitor. Review the page that actually reaches the responder. [Google SRE Workbook](https://sre.google/workbook/alerting-on-slos/) |
| FinOps Framework | Who owns the value and cost of the service across its lifecycle? | Allocate shared and direct cost, reconcile to the ledger, choose a unit of value and compare improvements under equal service quality. [FinOps Foundation](https://www.finops.org/framework/) |
| OpenGitOps principles | How is desired state declared, versioned, retrieved and reconciled? | For pull-based environments, test a source outage, out-of-band change and supervised pause/resume. For appliances, document the actual application and verification workflow. [OpenGitOps](https://opengitops.dev/) |
| SLSA build provenance | Why may this exact artifact enter the target environment? | Bind artifact digest to authenticated provenance and compare source, builder and parameters to expected values. Test rejection of a valid signature from an unexpected builder. [SLSA v1.2 verification](https://slsa.dev/spec/v1.2/verifying-artifacts) |
| NIST zero trust architecture | What evidence authorizes a specific principal to use a resource? | Prove same-network access without entitlement is denied, a token issued for another audience is refused, and revocation takes effect within the stated interval. [SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final) |
| Contingency planning and incident response | Can the team recover business use and learn from the disruption? | Establish recovery order and objectives, exercise the operator handoff and retain an integrity-checked restore timeline. [SP 800-34 Rev. 1](https://csrc.nist.gov/pubs/sp/800/34/r1/upd1/final) and [SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final) |
| OT security and Internet operational guidance | Which constraints depend on a specific operating environment or protocol? | Validate industrial changes against site process constraints. Evaluate IPv6 forwarding, ICMPv6 handling and policy parity with actual traffic. [NIST OT guidance](https://csrc.nist.gov/pubs/sp/800/82/r3/final) and [IETF RFC 9099](https://www.rfc-editor.org/rfc/rfc9099.html) |

## Use at review

Select the applicable rows, state the project's outcome, name its owner and attach the observed result or explicit gap. One restore exercise may inform several reviews, but only for the tested service, release, data volume and failure. Use the [readiness worksheet](../records/assurance/readiness.md) to keep the evidence boundary visible.
